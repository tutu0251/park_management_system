Integration API (reference)

Contract sketch for third-party systems. All paths are relative to your deployment base URL. Production would enforce RBAC and TLS.

Your session token (issued on sign-in in this mock):
—
Send as Authorization: Bearer <token> or use OAuth 2.0 client credentials in a real deployment.

Authentication & sessions

POST /api/register
Create a user (admin/service scope). New users may be created inactive pending activation.
POST /api/login
Authenticate with email/username and password. Returns session and API token.
POST /api/logout
Invalidate the current session / token.

User management

GET /api/users
List users. Admin only.
PUT /api/users/{user_id}
Update name, email, role, status. Admin only.
DELETE /api/users/{user_id}
Delete a user. Admin only.

Machines

GET /api/machines
Fleet list with reader status (Online, Maintenance, Offline, Error).
POST /api/machines/{machine_id}/status
Set operational status. Body: { "status": "Online" | "Maintenance" | "Offline" | "Error" }. Operators and admins.

Transactions

GET /api/transactions
Query log with filters (date range, card, reader, game, event type, location).
POST /api/transactions
Create a manual adjustment row. Admin only in the mock console.

RFID cards

GET /api/cards
List registered cards and balances.
POST /api/cards/{card_id}/checkout
Check out a card; response includes remaining credit to return to the guest.
POST /api/cards/{card_id}/activate
Activate a previously deactivated card (when business rules allow).

Rate limiting

Production APIs should return 429 Too Many Requests with a Retry-After header when a client exceeds a sliding window (for example 120 requests per minute per token + IP). Burst traffic from arcade POS integrations should be queued or throttled client-side. 

HTTP/1.1 429 Too Many Requests
Retry-After: 42
Content-Type: application/json

{ "error": "rate_limit_exceeded", "message": "Slow down and retry." }
